# 架构改进待完成清单

更新日期：2026-09-08。来源：本次全项目架构审查。

本清单记录待实现事项，不代表功能已经完成。保留当前 Main / Preload / Core / Database / Renderer 分层，按具体问题逐步改进；不引入通用 Agent 框架或路由重构。P1 优先处理，P2 随后推进，P3 按规模与需求安排。

## P1：统一 IPC 信任边界

- [ ] 在 Main 内封装可信 Renderer 来源校验，覆盖会话、偏好设置、模型设置和用量相关 IPC。
- [ ] 统一校验发送窗口、主 frame 和允许的页面来源，并补齐窗口导航限制。
- [ ] 统一外部输入校验和安全错误转换，避免原始异常跨进程暴露。

验收：合法窗口调用正常；非可信页面、子 frame、无效参数被拒绝。Preload 继续只暴露明确命名的业务 API。

## P2：为上下文添加上限

- [ ] 在 Core 中封装统一的上下文组装与预算计算方法，替换每次请求直接发送全部会话历史的方式。
- [ ] 为模型配置明确的上下文窗口上限、输出 token 预留量和安全余量；缺少模型信息时使用明确的保守默认值。
- [ ] 按 token 预算限制输入，预算包含系统指令、消息和工具定义等请求内容；估算方式及其误差需明确。
- [ ] 超过预算时优先移除最早的完整对话轮次，保留系统指令、最新用户输入，以及完整的工具调用与结果配对。
- [ ] 最新输入与必要指令本身超限时，返回可理解、已国际化的错误，避免发送必然超限的请求。
- [ ] 裁剪仅影响本次模型请求，数据库中保留完整历史；普通发送与重试使用同一套预算规则。
- [ ] 补充边界测试：刚好达到上限、超限、多轮历史、工具消息、单条超长输入和切换模型后的预算变化。

验收：长对话请求始终受所配置预算约束，不再随历史无限增长；原始历史不丢失，消息结构有效。历史摘要作为后续独立优化，不作为首版裁剪功能的前置条件。

## P2：LLM 多模型兼容与可靠性

- [ ] 集中管理模型能力与参数策略，包括流式响应、usage、tool calling、结构化输出和供应商扩展参数。
  - 2026-09-15：工具请求参数策略（`tool_choice`、`parallel_tool_calls`、DeepSeek thinking / reasoning effort）已收敛至 `src/core/llm/tool-request-policy.ts`，覆盖 vocabulary / phrase / synonym / vocabulary-practice 四个工具调用入口（见 `docs/plans/2026-09-15-llm-tool-protocol-refactor.md`）。流式响应、usage、结构化输出等其余参数策略仍待收敛。
- [x] 移除学习业务中的供应商域名 / 模型名特殊判断，将适配规则收敛到 LLM 层。
  - 2026-09-15：vocabulary / phrase 分析器中的 DeepSeek hostname / 模型前缀判断与两个多轮分析器中的 `parallel_tool_calls` 分支已移除，统一由 `src/core/llm/tool-request-policy.ts` 生成；synonym 分析器内基于 Gemini 协议的「整轮拒绝多工具并允许一次纠正」属执行流程而非请求参数，按计划保留原位。
- [ ] 将连接测试拆分为文本、流式和工具调用能力验证，避免一次非流式成功被视为所有能力兼容。
- [ ] 明确当前仅支持 OpenAI-compatible 协议；有原生协议接入需求时增加独立适配器及契约测试。
- [ ] 细化限流、服务端故障、认证、网络、超时与协议错误分类。
- [ ] 在总超时预算内实现有限重试，遵循 Retry-After；流式内容已经输出后，不自动重新生成并拼接结果。
- [ ] 为重试记录逻辑请求和独立尝试，确保用量统计、取消和终态记录正确。
- [ ] 按实际需要增加供应商级并发限制；故障切换仅使用用户明确配置的候选模型与策略。

验收：通过模拟限流、服务端错误、断流、超时和取消的测试；对声明支持的供应商执行能力验证。保留 complete 与 stream 的独立接口和生命周期。
