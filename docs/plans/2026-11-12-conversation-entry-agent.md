# 对话入口 Agent 实施计划

状态：已实施

日期：2026-11-12

## 1. 目标与范围

通过准入的新会话请求先由 Python 入口 Agent 识别意图。命中已注册的 subagent 时，执行对应的工作流。没有匹配时，把原始用户消息与会话历史交给现有普通对话工作流。一次请求只选择一条执行路径。

首版同时接入桌面对话现有的全部八个斜杠命令。每个命令均支持直接键入或通过选择器提交，并由同一 Python 入口分发。八个命令全部通过验收后才完成本计划。会话标题和练习通过各自的调用入口启动。

首版优先识别显式命令。桌面自然语言识别只覆盖已有的只读概念讲解，使用普通对话处理其他自然语言请求。翻译或润色并收藏通过显式 `/sentence` 触发。

| 命令                  | 参数                                 | 工作流与预期结果                                   |
| --------------------- | ------------------------------------ | -------------------------------------------------- |
| `/concept`            | 待讲解的词或表达，可留空并由对话澄清 | 流式讲解概念和用法                                 |
| `/vocabulary`         | 一个或多个词汇，沿用现有批量格式     | 分析、查重并收藏词汇，返回批次报告                 |
| `/phrase`             | 一个或多个短语，每行一个             | 分析、查重并收录短语，返回批次报告                 |
| `/explore-phrase`     | 无参数                               | 生成 10 个短语及释义、例句，保存到探索短语历史     |
| `/explore-vocabulary` | 无参数                               | 生成 10 个单词及释义、例句，保存到探索词汇历史     |
| `/synonym`            | 逗号分隔的单词                       | 按共同语义查询、归组并逐词提交，返回处理报告       |
| `/sentence`           | 一整段原文                           | 翻译或按目标语言润色并收藏整段，已收录时复用原记录 |
| `/tts`                | 待朗读的文本                         | 使用现有本地语音合成生成可播放音频                 |

例如，`解释一下 keep me posted 的用法。` 可进入概念讲解。`帮我把这句话翻译成英语。`、`/sentence-extra 示例`、`/unknown 示例` 和 `“/sentence” 怎么用？` 进入桌面普通对话。只输入 `/sentence` 时提示补充原文并保留草稿。

只识别当前请求的意图。沿用现有会话的空白规则定位消息开头的半角斜杠，命令名后须为空白或消息结束。正文中引用的命令、代码块内的命令和历史轮次中的命令作为内容处理。已注册命令缺少必填参数或参数非法时返回对应校验错误。已选工作流不可用、超时、取消或失败时结束该请求，避免再次执行或生成第二份回复。

## 2. 现有路径与入口设计

`ConversationModule` 当前分别处理普通文本和类型化技能提交。Renderer 的选择器和部分直输命令经 `runSkill` 提交，通信渠道的句子收录也走类型化提交。Python 的 `conversation/routing.py` 在普通会话任务内选择 `/concept` 或普通回复，`runtime/dispatcher.py` 按已绑定的 task 执行各工作流。八个命令已有对应 Python 工作流。 [对话技能架构](../architecture.md#对话技能执行边界) · [Agent Engine](../../agent-engine/README.md)

```text
桌面文本 / 选择器 / 已准入的渠道请求
  → ConversationModule 登记请求、冻结语言和调用方权限
  → Python 入口图识别意图，返回经校验的工作流标识或普通对话
  → 宿主绑定该工作流已有的参数、权限、预算及执行身份
  → Python 执行选中的工作流，宿主沿用原有事件与提交路径
```

- 在 `agent-engine/src/lingo_agent/workflows/conversation/` 增加入口图和涵盖八个命令的静态工作流映射，由 `runtime/dispatcher.py` 暴露独立的会话路由任务。入口返回单个带类型的结果，区分普通对话、已选工作流和已识别命令的输入错误。将 `/concept` 的判断迁入入口，普通对话任务接收已经确定的回复类型。
- 斜杠命令使用确定性匹配。TS 只提取通用的命令首词和参数范围等信息，参数正文绑定在宿主。Python 根据注册表决定工作流，未知命令直接进入普通对话。宿主校验终态与本次请求、候选权限和原始输入一致，再使用原有技能 schema 校验和绑定参数。各工作流继续通过自己的协议交换所需数据。
- 桌面自然语言使用最多一次受限的意图分类调用，候选仅包含概念讲解和普通对话。Python 持有分类 Prompt，明确讲解语言、目标学习语言及仅返回协议枚举的要求。宿主向现有模型传输层传入绑定的最新消息，校验枚举后只返回小型回执。分类结果明确为普通对话、意图不明或缺少可独立识别的概念时，进入普通对话。供应商失败、超时或结果格式无效按现有安全错误处理。
- 新路由任务只允许上述分类操作，无业务写入、工具调用或流事件。初始预算拟设为含启动和排队 15 秒、供应商 10 秒、最多 1 次模型调用，输入按现有会话文本上限及 Prompt 大小计量。技能工作流另起绑定运行，沿用各自的操作白名单和预算。宿主通过判别联合绑定一个工作流，校验对应终态后才释放结果。

## 3. 接入与恢复

- **桌面。** 八个命令均可用 `send` 直输，包括目前主要通过选择器提交的 `/vocabulary`。选择器提交也交给同一入口，现有类型化 `runSkill` 作为兼容入口。Renderer 保留命令补全、草稿、参数提示和结果展示，未知命令可正常提交。保留现有参数长度限制，单独计量命令前缀与正文，并回归多行参数和 `/tts` 有意义的空白。错误提示使用现有中英文资源，必要时同步新增 key。
- **通信渠道。** 入口依据已持久化的操作和当前绑定权限接收学习请求。渠道 `chat` 走普通对话，已授权的 `/sentence` 走统一入口及句子工作流。`/bind`、`/confirm`、`/help`、`/new`、`/cancel` 和 Telegram 的 `/start` 由通信控制层按各自的准入规则处理。 [公共通信接入指南](../communication-adapters.md)
- **请求生命周期。** 路由前建立请求归属和会话互斥。路由与选中的工作流分别使用各自的 Python 运行身份，并共享一个宿主请求身份、语言快照和取消信号。保存前取消或窗口销毁时结束待提交请求，保留草稿。确定路由后按已有路径保存用户消息，保存成功才发 `started`，随后发出唯一终态。标题任务在路径确定后按原规则启动，包括 `/tts` 的本地标题。
- **提交与重试。** 词汇、短语、句子和 TTS 沿用各自的事务与执行报告，近义词沿用逐词提交，两个探索工作流按各自的批次身份恢复。已有技能执行依据持久化的技能、参数和阶段恢复，已提交结果从对应报告或历史批次恢复。没有技能执行记录的普通对话重试仅允许只读回复，避免旧消息因新增工作流变成写入操作。按现有 SQLite 和 JSON 格式设计，并覆盖升级前记录。

## 4. 实施顺序与验收

| 阶段              | 工作与完成条件                                                                                                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 路由图与协议   | 先为八个命令编写 Python 路由和 TS 契约的失败用例，再实现静态映射、输入描述和类型化终态。验证完整命令匹配、各自参数规则、显式命令零分类调用、无匹配进入普通对话，以及拒绝伪造或越权终态                                                                     |
| 2. 全部命令接入   | 同一批接通八个命令的桌面直输与选择器提交，迁移对应的旧执行分派。用组件测试验证所有命令的两种提交方式，用可控模型或语音替身、临时存储和真实 Python JSONL 验证每个命令只执行其对应工作流。回归渠道授权的普通对话和句子收录、其他学习命令的权限拒绝及控制命令 |
| 3. 生命周期与恢复 | 回归八个命令的 Prompt、参数边界、标题、流事件、技能阶段和结果展示。验证句子查重与唯一提交、近义词部分提交、两种探索历史隔离与恢复、TTS 历史播放，并覆盖路由前后取消、窗口销毁、同会话竞争、工作流失败和升级前记录                                          |
| 4. 自然语言识别   | 以中英文用例覆盖明确概念、普通翻译、模糊问题、命令讨论和恶意结构化指令。验证分类最多一次、只读候选校验、无匹配时普通对话收到原历史、失败时仅有一个终态，并记录路由耗时和模型调用数                                                                         |
| 5. 构建与文档     | 更新架构和 Agent Engine 文档。由 TS Zod schema 生成 JSON Schema，升级破坏性协议变更的版本、握手能力和运行包 manifest。在目标 OS/CPU 原生重建，烟测覆盖八个命令的路由和普通对话                                                                             |

全量 TS 测试前确认 Python 锁定环境已同步。首次准备或锁文件变化后运行 `pnpm agent:sync`。实现完成后执行以下验证。

```bash
node --experimental-strip-types scripts/agent-protocol-schema.mjs
pnpm agent:protocol
pnpm agent:test
pnpm agent:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm agent:build
pnpm agent:smoke
```

任何 E2E 测试执行前须取得用户明确许可。未获许可时记录「E2E 未执行，按约定默认无问题」。验证使用临时数据库。真实用户数据库变更须单独征询用户。全部计划工作及相关验证完成后，将本计划状态改为「已实施」。
