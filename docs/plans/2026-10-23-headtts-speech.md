# HeadTTS 文本转音频与单词播放定位实施计划

- 日期：2026-10-23
- 状态：实施中（功能开发与本机自动验证已完成；人工声学、设备同步及跨平台验收待完成）
- 模型精度：固定 FP32
- 核心交付：文本转音频，并能在播放期间准确查询音频游标对应的单词及其原文位置。

## 目标与范围

本计划落实三项要求：

1. 引入 HeadTTS，完成本地文本转音频。
2. 提供可查询、可订阅的单词播放位置，支持界面随播放高亮正确的单词。
3. 使用 FP32 模型权重和推理配置，不自动降级到 FP16、INT8、Q4 等其他精度。

首版面向项目当前支持的英语，接入单词、短语和英文例句的手动朗读，提供播放、暂停、继续、停止及按音频时间跳转。设置包含音色和合成语速；界面语言继续支持简体中文和英语。先完成整个请求的合成、时间轴校验与音频解码，再开始播放，减少分段到达和调度对同步的影响。

流式对话边生成边朗读、完整 Markdown 自动提取朗读、多语言合成、语音识别、发音评分和虚拟人口型不属于首版。HeadTTS 当前的英语限制及其音频、时间戳能力见[官方 README](https://github.com/met4citizen/HeadTTS#readme)。

本计划已进入实施阶段。实施和验收遵循项目的 TDD、真实用户数据库及 E2E 许可规则；开发验证使用隔离资源及临时目录，不访问真实用户数据库。

## 架构决策

采用“可信宿主合成、独立进程推理、Renderer 播放”的结构：

```text
Renderer 朗读入口
  → window.api.speech.synthesize
  → Main 受信任 IPC
  → Core SpeechService
  → SpeechSynthesizer 接口
  → Main HeadTTS 适配器
  → utilityProcess 中的 HeadTTS Node Worker
  → 宿主校验后的音频、原文映射与单词时间轴
  → Renderer Web Audio 播放控制器
  → 当前播放单词查询与界面高亮
```

- Core 持有文本、语言、音色、预算、结果及时间轴的校验与请求协调，不依赖 Electron 或 React。
- Main 管理进程、固定入口、受控资源路径、窗口归属、设置存储和错误映射，实现并注入 Core 的合成接口。
- 独立进程只加载合成所需资源和执行推理，不持有数据库、模型 API Key、学习历史或完整会话。
- Renderer 只使用浏览器音频 API 与窄桥接接口；播放时钟、暂停位置和高亮属于应用级播放状态。
- 用户点击朗读是确定性的宿主能力，不新增 Python Agent 任务。将来若增加 Agent 自主安排听力的策略，再在 `agent-engine/` 扩展受控宿主调用。

`utilityProcess` 是 Electron 提供的 Node 子进程能力，使用进程消息通信，无需为应用内部合成开放 HTTP/WebSocket 监听端口。详见[官方 API](https://www.electronjs.org/docs/latest/api/utility-process)。

HeadTTS 的浏览器入口不是可直接运行于 Node 的通用合成类。需要为其 Node Worker 建立小型适配层，固定验证过的依赖版本，并用契约测试约束内部消息格式。实现前先验证当前 Electron 下的 Worker、ONNX 原生依赖及打包可用性；验证未通过时保留明确问题，不默认切换架构或精度。

## FP32 与资源管理

使用 `onnx-community/Kokoro-82M-v1.0-ONNX-timestamped`，实施时固定已验证的模型 revision、HeadTTS 版本和完整依赖锁文件；不以持续变化的 `main` 或 `latest` 作为生产资源身份。

- 首版固定 CPU 后端、`dtype: 'fp32'`、单个合成 Worker，先验证正确性和资源开销。
- 资源 manifest 记录模型 revision、FP32 权重文件列表、SHA-256、音色、词典及许可。加载前校验资源完整性和精度身份，运行时就绪回执必须与宿主预期一致。
- FP32 指模型权重和推理配置，不能仅凭返回音频是 `Float32Array` 判断模型精度。输出可以采用 24 kHz、单声道 PCM16 WAV，音频编码与模型精度分别校验。
- 后续若启用 WebGPU，同样显式指定 FP32，单独验证目标 OS/CPU 和驱动；不因内存不足、加速失败或加载失败自动降低精度。
- 采用受控首次安装：设置页提供资源安装入口和进度；首次朗读发现未安装时显示明确状态。Main 从固定来源下载，先写临时目录，全部校验成功后原子启用；安装完成后的朗读不再请求网络。
- 模型与音色放应用管理的用户数据子目录 `speech/models/<revision>/`，独立于 SQLite；运行期间禁止第三方库隐式下载缺失文件。缓存路径由 Main 决定，不依赖当前工作目录或 `node_modules` 的可写性。
- 运行入口与 JS 依赖随应用分发，ONNX 原生库按目标平台打包并正确解包；设置不向 Renderer 暴露磁盘路径或允许指定模型 URL。

HeadTTS 的 Worker 将 `dtype` 传给模型加载器，支持单词时长数据随音频返回；具体行为以实施时锁定版本的契约测试为准。参见[官方 Worker 实现](https://github.com/met4citizen/HeadTTS/blob/main/modules/worker-tts.mjs)。

## 单词时间轴与原文映射

### 时间来源

直接使用 HeadTTS 返回的 `words`、`wtimes` 和 `wdurations`，时间单位为毫秒，转换为相对最终音频起点的秒。时间戳随同一次推理产生的音频一起绑定；不按字符数量、平均语速、模型调用开始时间或 IPC 返回时间估算单词位置。字段含义见[官方合成结果协议](https://github.com/met4citizen/HeadTTS#response-audio)。

适配层显式设置 `deltaStart: 0`、`deltaEnd: 0`，避免将口型展示的提前或延后偏移带入单词定位。HeadTTS 根据模型时长和帧率构建时间戳；该信息不是外部强制对齐得到的声学真值，必须分别验证时钟同步和实际发音边界。

### 文本与分段规则

- 请求只接受明确标记为英语的纯文本，不把 Markdown 标记、HTML、任意 HeadTTS 输入对象或会话全文直接透传给第三方运行时。
- 为每次请求保存不可变文本和配置快照；来源内容变化后旧音频和高亮失效，不能继续套用旧下标。
- 用保留 UTF-16 范围的切片拆分句子和长文本，保留完整原文到送入模型文本的映射；不在单词中间或代理对中间切分。
- 每段还必须验证实际音素 token 预算。第三方 tokenizer 的静默截断不能成为正常行为；超限时继续有界分段，无法安全分段则明确失败。
- 分段串行合成、解码后按实际采样帧拼接，不做交叉淡化、时间拉伸或隐式裁剪。所有词的全局时间加上前面音频的实际时长，不能只累计最后一个词的结束时间。
- 上游词条可能包含空格和标点。按返回顺序重建文本并验证映射，用累积范围定位重复词；禁止用全局 `indexOf(word)` 查找原文。
- 缩写、所有格、连字符、数字、Unicode 撇号和换行使用固定回归样本验证。若存在规范化展开，保留明确的一对多映射；无法确认映射的结果整体失败，不能伪造均匀时间戳。

### 对外数据契约

合成结果至少包含请求身份、不可变文本、语言、音色、合成语速、音频字节、音频时长和单词列表。每项包含：

```ts
interface SpeechWord {
  index: number // 当前合成结果中的稳定顺序身份
  text: string // 对应原文的展示文本
  charStart: number // 原文 UTF-16 起点，包含
  charEnd: number // 原文 UTF-16 终点，不包含
  startSeconds: number
  endSeconds: number
}
```

宿主校验数组长度一致、数字有限、范围合法、顺序稳定、时间在实际音频范围内，以及每项原文范围与内容匹配。零时长、负时长、无法解释的重叠、越界或缺失时间戳均作为合成结果错误处理；仅允许对毫秒时间戳取整及采样取整产生的边界误差做明确归一化，容差不超过 1 ms 加一个采样周期。不能把明显异常值简单裁剪后继续播放。

非发音的纯标点片段不创建单词；其停顿仍保留在音频时间轴。单词是本次 HeadTTS 对齐单元，不用另一套 UI 分词器重新排列或平均分配其时间。可见范围需去除词条两侧的空白和附带标点，同时保留这些字符在原文中的位置。

## 播放时钟与当前单词查询

### 唯一播放时钟

Renderer 使用专用 `AudioContext` 和 `AudioBufferSourceNode` 播放解码后的音频，以音频设备输出时间作为定位依据。优先使用 `getOutputTimestamp()` 将设备输出的 `contextTime` 与 `performanceTime` 对应起来；它们的定义见[Web Audio 规范](https://www.w3.org/TR/webaudio/#dom-audiocontext-getoutputtimestamp)。

一次播放记录 `scheduledStartContextTime` 和 `offsetSeconds`。对有效、正在运行的输出时间戳，计算当前输出时刻并换算为音频游标：

```text
outputContextTime = timestamp.contextTime
                  + (performance.now() - timestamp.performanceTime) / 1000

positionSeconds = offsetSeconds
                + outputContextTime - scheduledStartContextTime
```

- 只有音频实际到达计划起点后才进入有效单词区间；起播前不能因为游标裁剪到 0 就提前高亮首词。
- `requestAnimationFrame` 只驱动可见 UI 刷新，不累积播放时间，也不为每个词预设 `setTimeout`。
- 音频暂停、context suspended/interrupted、系统休眠或输出时钟无效期间禁止沿墙上时间外推；保存冻结游标，恢复时重新读取输出时间戳并建立锚点。
- 当前目标 Electron 上必须实测输出时间戳可用性。若无法获得有效时钟，明确返回播放时钟错误，不以估算计时冒充准确定位。
- 音频渲染结束回调不等于设备已经输出完最后一帧；结束状态与最后单词清理需覆盖设备输出尾部，避免高亮提前消失。

### 查询语义

播放控制器提供同步 `getPlaybackSnapshot()` 和状态/单词变化订阅。快照包含 `playbackId`、来源身份、状态、`positionSeconds`、`durationSeconds`、`currentWord` 及是否正在播放；`currentWord` 同时带稳定 index 和原文范围。

- 播放中按 `startSeconds <= positionSeconds < endSeconds` 查询，使用二分查找；同一词重复出现时以 index 区分。
- 时间轴没有单词覆盖的起始等待、间隙及尾部区间返回 `null`，不把上一词无限延长到下一词。此规则指时间轴中的间隙，不承诺识别词内每个声学静音片段。
- 暂停后快照位置及对应单词保持冻结，状态明确为 `paused`；此时 `currentWord` 表示游标所在词，不表示仍有声音输出。
- 继续播放或跳转时创建新的 source 节点，以保存或指定的 offset 播放，重新记录计划起点并立即重新查询；不重复累计旧播放时间。
- 首版 `playbackRate` 固定为 1。语速改变通过重新合成生成配套音频和时间轴，不对已含语速影响的时间戳再次除以语速。
- 停止、取消、失败和播放完成后清空当前词。新请求替换旧请求时递增播放代次，旧合成结果、旧事件和旧节点回调均不能改变新播放状态。
- 即时查询直接根据当前音频时钟求值；订阅与 React 展示可以按帧刷新。恢复可见性后重新计算，不能回放后台积压的逐词事件，也不声称后台 JS 能保证实时回调。

## IPC、安全与生命周期

`window.api.speech` 首版提供 `synthesize`、`cancel`、`getSettings`、`updateSettings`、`getRuntimeStatus`、`installResources` 及必要状态订阅。暂停、继续、停止、跳转和播放位置查询由 Renderer 播放控制器提供，避免逐帧往返 Main。

- channel、输入、结果和安全错误统一在 `src/shared/speech.ts` 定义；主进程和 preload 均按 schema 校验，现有 `LingoMateApi` 引用独立 `SpeechApi`。
- 合成和取消绑定发起窗口与请求 ID，注册和取消必须校验 owner；窗口销毁时取消其请求。状态订阅只发送经校验的最小业务数据。
- 字节与单词数据限长后通过 IPC 返回。Renderer 不接收进程对象、绝对路径、原生句柄、原始异常或第三方完整元数据；不需要口型时不返回 visemes。
- 首版使用一个共享推理进程和一个执行中的合成请求，排队数量有界。新朗读替换本窗口旧请求，跨窗口请求不能互相取消。
- 取消立即终止本地播放并撤销请求结果接收资格。若推理没有可靠的中断 API，丢弃迟到结果；超过硬截止时终止运行实例并使受影响请求明确失败。下一次显式请求可以新建进程，失败请求不自动重放。
- 运行时状态与播放状态分别管理：前者至少包含未安装、安装中、未加载、加载中、就绪和失败；后者至少包含空闲、合成中、播放中、暂停、完成、取消和失败。
- 实施时集中定义并测试预算。单次原文上限为 4,000 个 UTF-16 单元、每段 350 个 UTF-16 单元且满足模型 token 上限、最多 20 段、总音频 360 秒、音频字节 24 MiB；超限明确拒绝，不返回部分成功。
- 资源安装使用独立、可取消的下载流程；已安装后的单次合成总截止 180 秒（含冷启动），加载阶段最多 120 秒、单段模型执行最多 60 秒，均受总截止约束。
- 第三方 stdout/stderr 由 Main 有界接收、脱敏后写本地诊断日志，不进入 Renderer 或控制台；默认关闭文本和音素 trace。

## UI、设置与缓存

- 使用应用级单一播放控制器，首次点击朗读建立音频上下文；只允许一段可听播放，切换来源时停止旧播放并清理高亮。
- 通用 `SpeakButton` 与 `SpeechText` 接入已有单词、短语及英文例句展示位置；纯文本组件按契约范围切片，保持原有空白、标点、复制和选择行为。
- 页面切换时停止当前播放，但已加载模型可以复用；对话视图仍按现有架构保持挂载。进入语音设置和退出时遵循既有焦点管理。
- 音色从已安装白名单选择；首版合成语速限制在 0.75–1.5。修改设置只作用于新请求，正在播放的音频继续使用其配置快照。
- 设置使用独立配置存储，不新增 SQLite 表；首版音频和时间轴只做有界内存缓存。缓存键包含实际合成文本、语言、音色、语速、模型 revision、FP32、分段/对齐版本，禁止跨配置复用不匹配结果。
- 静态文案、错误、按钮及无障碍标签在 `zh-CN` 与 `en` 同步国际化；高亮不只依靠颜色表达。屏幕阅读器不逐词触发 live region，播放控件正常提供键盘与状态反馈。

## 实施步骤与测试

### 1. 固定依赖与可行性验证

- 在隔离目录验证锁定版本 HeadTTS Node Worker、FP32 模型和当前 Electron `utilityProcess` 的组合，记录版本、冷/热启动耗时、内存峰值、音频与时间戳样本。
- 验证资源可本地加载且缺失时不会隐式联网；验证运行入口和原生库在开发及打包布局中都能解析。
- 先验证普通句子、重复词、不同合成语速及段尾停顿的时间轴。若上游时间戳或文本映射不能达到后述验收标准，定位并修正适配/上游问题；若需要新增强制对齐组件，应先更新本计划，不能用估算替代。

### 2. Core 与运行时

- 逐行为 TDD：先写并确认输入预算、FP32 拒绝降级、分段边界、文本映射、时长校验、取消及迟到结果的预期失败，再实现 Core 和适配层。
- 第三方契约测试覆盖 `words/wtimes/wdurations`、零偏移配置、实际采样时长、token 超限、错误响应和协议失配；使用替身完成确定性测试。
- 真实运行时集成测试使用临时配置和资源目录，无网络、无真实用户数据库；资源准备作为显式前置步骤，缺失时报错，不能静默跳过关键验证。

### 3. IPC 与播放定位

- IPC 测试覆盖不可信来源、schema 错误、跨窗口取消、重复请求、窗口销毁、进程退出与资源预算。
- 以可注入音频时钟测试查询区间、重复词、静音间隙、起播等待、设备输出延迟、暂停、恢复、跳转、context 中断及旧播放回调。
- 逐词位置查找与原文映射测试保持纯函数；音频播放器测试公开播放行为，不依赖 React 私有状态。

### 4. UI 与分发

- 组件测试覆盖词条朗读、高亮、按钮状态、键盘操作、页面切换、双语文案和设置快照；使用可控合成与音频替身。
- 配置独立入口构建、外部依赖、资源 manifest 和原生库解包；macOS/Windows/Linux 及各目标 CPU 分别执行原生构建和安装布局验证，记录各平台结论。
- E2E 用例覆盖真实 Electron 播放、暂停、跳转、停止及新旧请求隔离；执行前取得用户明确许可。模型资源预置于测试专用目录，使用临时用户目录，不访问真实学习数据库。

## 验收标准

| 要求           | 可观察的完成条件                                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| HeadTTS 转音频 | 支持范围内的英文文本生成可解码、可播放的完整音频；安装后断网可用，失败不会停留在加载或播放状态                                                                                                         |
| 固定 FP32      | manifest、实际加载参数及运行时身份一致；缺失 FP32 或模拟内存/后端故障时明确失败，没有精度降级路径                                                                                                      |
| 正确原文位置   | 固定回归集所有单词的 index 和 UTF-16 范围正确，重复词及规范化映射不串位，原文不会被高亮过程改写                                                                                                        |
| 时钟定位正确   | 注入时钟下区间查询全部通过；暂停、继续、跳转、起播延迟和请求替换不漂移、不接收旧事件                                                                                                                   |
| 设备播放同步   | 在有许可的目标 Electron 验收中，前台正常负载下，词变化相对输出音频时钟的展示/订阅延迟 P95 ≤ 50 ms；长音频不累计漂移                                                                                    |
| 实际发音对齐   | 固定至少 30 条英语样本、200 个可辨识词边界，覆盖重复词、缩写、标点、分段和 0.75/1/1.5 语速；以人工复核的实际音频边界为参考，起点绝对误差 P95 ≤ 100 ms，全部最大误差 ≤ 200 ms，并检查结束边界和句尾停顿 |
| 控制完整       | 暂停冻结、恢复连续、跳转重算、停止清空；音频输出尾部和页面隐藏/恢复无陈旧高亮                                                                                                                          |
| 边界与分发     | IPC 来源和归属校验通过，Renderer 无高权限依赖，各声明支持的平台通过 FP32 加载和播放定位验收                                                                                                            |

上述延迟是本项目的验收门槛，不是已经测得的结果，也不是 HeadTTS 的官方精度承诺。测试报告记录 OS/CPU、Electron 版本、音色、模型 revision、输出设备和测量方式；先使用固定有线/内置输出设备建立基线，再记录其他设备结果。任意蓝牙设备的实际声学延迟不能仅凭 JS 时钟宣称已精确测量。

若声学对齐未达标，即使音频可播放、时间轴查询正确，也不能将“准确读取当前单词”标为完成；需要修正并重新测量，不通过放宽门槛或隐去异常样本通过验收。
