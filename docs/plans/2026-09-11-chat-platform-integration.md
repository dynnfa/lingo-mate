# 聊天平台接入实施计划

- 日期：2026-09-11
- 状态：待实施

## 目标与范围

让用户通过 Telegram、微信等聊天平台与 Lingo Mate Agent 通信，在聊天中完成单词收藏、学习问答等操作，并在桌面端查看同一份词库中的结果。

本次只编写计划，不实现功能、不连接真实账号、不修改用户持久化数据。实施分为 Telegram MVP 和微信接入两个阶段；仅完成 Telegram 时，本计划仍保持未完成状态。

首版面向单个桌面用户的已绑定私聊账号，支持文本对话、显式单词收藏、自然语言收藏意图确认、查看本次执行结果和取消请求。暂不包含群聊、语音、图片识别、文件处理、远程删除词条、定时推送和多租户服务。短语收藏等能力在基础链路完成后复用已有技能扩展。

## 当前代码基线

- `src/core/conversation/conversation-module.ts`：已有创建会话、发送消息、运行技能、事件回调和取消能力，是外部消息接入的复用入口。
- `src/core/learning/vocabulary/vocabulary-conversation-skill.ts`、`vocabulary-module.ts`、`vocabulary-insert.ts`：已有单词收藏领域能力，外部平台应复用同一套校验、分析和存储规则。
- `src/database/sqlite-vocabulary-repository.ts`：已有本地词库仓储，不为每个平台复制词库。
- `src/main/conversation-ipc.ts`：现有请求所有权依赖 WebContents，外部平台需要独立的身份和请求归属管理，不能伪造 Renderer IPC 请求。
- `src/shared/conversation.ts`、`src/preload/`：已有桌面对话协议；新增平台设置 API 保持窄接口。

## 平台策略与运行方式

### Telegram：第一阶段

使用 Bot API，以 long polling 为桌面 MVP 的接收方式，避免首版要求用户部署公网回调服务。Telegram 的 `getUpdates` 与 webhook 不能同时使用；接入时检测冲突并给出可操作提示，不自动删除已有 webhook。参考：[Telegram Bot API](https://core.telegram.org/bots/api#getupdates)。

由 Main 管理连接启动、停止、退避重连和应用退出清理。首版仅在桌面应用运行、系统未休眠且网络可用时处理消息；不承诺关闭应用后仍能实时响应。恢复后按明确的消息有效期处理积压消息，过期写入请求需用户重新发起，避免突然执行旧指令。

### 微信：第二阶段

“微信接入”需要先选定具体形态：个人微信聊天、公众号或企业微信。它们不能视为同一种接口，本计划不把公众号或企业微信自动等同于用户期望的个人微信通信。

实施前用目标账号和官方文档验证：能否双向接收与回复、账号资格、认证方式、消息时限、重试规则及部署要求，并记录选择结果。若需要公网回调，设计最小转发服务，通过鉴权的出站连接把消息交给桌面端；转发服务不执行 Agent 或访问本地词库。部署成本和消息经过第三方服务的范围需在方案确定时说明。

微信阶段先完成真实账号的文本收发验证，再接入统一入口与单词收藏流程；若目标形态不可用，明确记录阻塞原因和替代选项，不以单向通知或模拟适配器宣称微信接入完成。

## 用户流程

1. 桌面设置新增“聊天平台”菜单：配置连接、查看连接状态、绑定账号、撤销绑定和断开连接。
2. 用户在桌面生成短时有效、一次性的绑定码，在目标平台发送绑定命令，并在桌面核对平台与账号后确认绑定。限制尝试次数；未绑定账号不能访问模型、词库或会话。
3. 已绑定账号可发送普通学习问题，Agent 在该外部会话中回复。
4. 发送 `/save apple` 表达明确收藏授权，直接复用现有单词技能；发送“帮我记住 apple”时，先展示识别出的词及学习语言，确认后执行。确认绑定到原始消息、词条快照和当前账号，并设有效期，不能用其他会话的“确认”触发写入。
5. 实际存储成功后回复收藏结果；重复词按现有领域规则反馈，失败时不声称已保存。桌面词库刷新后可看到相同词条。
6. `/new` 开启新的外部上下文，`/cancel` 取消当前账号会话中的执行，`/help` 显示支持的操作。取消不回滚已经提交的收藏，回复应准确说明结果。

平台回复中的静态文本、设置页、错误提示和无障碍标签均使用统一 i18n，覆盖项目支持的全部语言。每次实际模型请求显式传入解释语言和学习语言；例句与释义分别声明语言，不依据平台或消息文字猜测用户设置。

## 架构与职责

```text
Telegram / 微信
  -> 平台适配器（接收、校验、发送）
  -> Core 聊天入口（绑定鉴权、会话映射、幂等、命令分派）
  -> ConversationModule / 已有学习技能
  -> 本地仓储

Renderer 设置 -> Preload 窄 API -> Main 连接生命周期与凭据管理
```

- 新增 `src/core/channels/`：平台无关的消息入口、身份绑定规则、会话映射、执行状态和适配器接口；通过依赖注入调用会话服务、仓储及平台收发能力。
- 新增 `src/main/channels/`：平台网络适配实现、连接装配和生命周期管理；平台 SDK、网络凭据不进入 Renderer。
- 新增 `src/shared/chat-channels.ts`：可序列化设置展示类型、状态、错误码、校验 schema 和 IPC channel，不包含运行时实现。
- 新增 `src/renderer/src/settings/channels/`：菜单专属组件、hooks 和测试。同步更新 preload 实现及类型声明，暴露配置、绑定确认、状态查询、断开等明确 API，不暴露任意 URL 请求或原始 IPC。

统一入站消息至少包含平台、连接 ID、平台消息 ID、发送者 ID、聊天 ID、可选话题 ID、发送时间和文本。出站目标由已校验的入站上下文生成，不能由模型提供任意收件人。

会话键由平台、连接、发送者、聊天及话题共同确定，映射到内部 sessionId；外部消息不能指定已有桌面 sessionId。不同平台默认隔离对话上下文，但共享绑定桌面用户的词库。取消、确认和结果投递均校验同一归属。

## 执行可靠性与安全边界

- 同一外部会话串行执行，设置队列长度、输入长度和账号速率限制；超过限制时提供明确反馈。不同会话遵守现有模型并发约束。
- 以平台、连接和消息 ID 建立幂等键。持久化接收记录后才推进接收游标；重投消息不重复触发模型或收藏操作。
- 区分“已接收、待确认、执行中、执行成功、失败、已取消”和“回复待发送、已发送、发送失败”。词库提交与执行成功记录需要可靠关联，避免崩溃后重复执行写入。
- 使用持久化出站记录重试回复；回复失败只重发已有结果，不重新调用收藏技能。平台发送结果不明确时允许出现重复回复，但不能导致重复业务写入，不承诺跨平台严格 exactly-once 投递。
- 重启后恢复已完成任务的待发回复；执行状态不明确的任务先检查提交记录，无法确认时提示用户核对，不盲目重跑。启动、断开、退出、超时及取消均收敛至明确状态。
- Token 等凭据仅在 Main 安全存储和使用；设置表单提交后清空，不提供明文回读接口。日志不记录 Token、消息正文、学习记忆或包含凭据的请求 URL。
- 平台消息与模型输出均视为不可信输入，使用 schema 校验。远程可执行能力采用白名单，不允许任意文件、SQL、系统命令、模型配置修改或远程删除操作。
- 外发内容限于当前请求所需的回复，不自动发送桌面会话历史或完整词库。平台格式转义、消息长度限制和分段在适配器处理；首版聚合最终答复，不逐 token 外发。

## 持久化设计与实施前置条件

预计新增连接配置、账号绑定、外部会话映射、入站执行记录、接收游标和待发回复记录；具体表结构在实施时结合现有迁移与会话仓储确定。凭据与普通业务数据分开存放，为消息记录确定最小保留内容、保留期限及清理策略。

根据项目约定，执行数据库迁移或用户持久化数据变更前必须先询问用户，取得意见后再执行；本计划不构成执行迁移的授权。先在临时数据库验证迁移、事务边界和恢复流程，不直接操作真实词库。

## 实施步骤

1. 明确统一协议、远程能力白名单、绑定流程及 Telegram MVP 验收用例；列出新增持久化结构并完成实施前确认。
2. 实现 Core 入口、命令分派和技能复用，用假平台、假模型及临时仓储打通“绑定 → 收藏 → 结果回复”。
3. 实现幂等、会话隔离、取消、崩溃恢复和出站重试，验证写入与回复失败不会互相触发重复执行。
4. 实现 Telegram 适配器及 Main 生命周期，验证真实私聊收发和连接恢复。
5. 完成桌面设置、preload API、状态与双语文案；打通桌面词库与平台收藏结果验收。
6. 确认微信接入形态，完成真实收发验证和必要的转发部署方案，再实现微信适配器并复用同一组契约测试。
7. 完成两个平台的端到端验证，补充接入、解绑、离线限制和故障排查文档。全部计划工作与验证完成后，将状态更新为“已实施”。

## 验证与验收

- Core：未绑定请求拒绝、绑定码过期与重放、确认归属、会话隔离、并发排队、取消、无效输入、学习语言快照和技能失败反馈。
- 存储与恢复：重复消息、重复词、写入成功但回复失败、游标恢复、提交中断、重启后补发、过期消息不自动写入。
- 适配器：收发协议校验、认证失败、断网退避、限流、超长回复、格式转义、停止后不再接收；微信选型后增加对应验签及重放验证。
- Main / Preload / Renderer：可信 IPC 来源、凭据不回读、绑定确认、状态更新、断开连接、中英文和键盘可访问性。
- 单元测试放在模块 `__tests__/`，跨模块测试放在 `tests/integration/`，端到端测试放在 `tests/e2e/`。自动化使用假平台和假模型，不依赖真实账号或产生真实外发消息。
- 真实账号验收：Telegram 和最终选定的微信形态分别完成“绑定 → 学习问答 → 收藏单词 → 平台收到准确结果 → 桌面词库可见 → 重投不重复写入 → 解绑后拒绝访问”。真实外发验证需在用户明确授权的测试会话中进行。

实施完成后运行相关测试及 `pnpm lint`、`pnpm typecheck`、`pnpm build`。本次仅新增 Markdown 计划，检查文档与差异即可。
