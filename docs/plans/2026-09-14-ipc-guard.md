# IPC 守卫统一封装计划

- 日期：2026-09-14
- 状态：已实施（2026-09-17，见文末实施记录）
- 关联：`docs/architecture-review-2026-09-11.html` 第二点、`docs/architecture-todo.md` P1「统一 IPC 信任边界」

## 目标与范围

在 Main 层提供统一的 `registerTrustedHandler`，让全部 Renderer → Main 的 IPC 请求入口强制执行：

1. 来源检查。
2. 输入校验、异常捕获和安全错误转换。
3. 返回结果校验。

覆盖当前九个模块的全部 32 个 `ipcMain.handle` 注册：conversation、preferences、models、usage、vocabulary、phrase、synonym、vocabulary-practice、sentence-practice。实施时重新核对 channel 清单，覆盖期间新增的入口。

本次不合并业务服务，不重构流式事件、请求所有权、取消和并发控制，不引入通用中间件框架。Main → Renderer 的推送事件继续使用现有事件 schema，不属于请求注册器的返回结果。窗口导航限制属于关联 P1 的另一项工作，不在本计划内，因此完成本计划不等于整个 P1 已完成。

## 当前问题

- 七个 IPC 模块分别复制了 `isTrustedSource`，安全策略依赖每个 handler 手动调用。
- conversation 的 create/list/load/send/retry/cancel 缺少来源检查；runSkill 已有检查，但 `rendererUrl` 可选，省略时跳过检查。
- conversation 的 load/send/retry/cancel 使用抛出式输入 `.parse()`，校验异常没有统一转换为安全结果。
- preferences 三个入口均缺少来源检查。
- 各入口输入校验、异常映射和结果校验的实现方式不同；部分只校验成功结果中的一个字段。
- models 和 preferences 已有具体的字段级输入错误码，收敛时需要保持这些语义。

## 设计

### 模块与注册接口

新增 `src/main/ipc-guard.ts`，承载来源策略和唯一的底层 IPC 请求注册入口。由 Main 装配可信页面配置，配置必须存在且有效，禁止省略配置后默认放行。

采用具名配置对象，避免位置参数增长。注册配置包括：

| 配置 | 职责 |
| --- | --- |
| `channel` | 使用 shared 中已有的 channel 常量 |
| `inputSchema` | 校验原始输入；无参数入口显式使用 undefined schema |
| `resultSchema` | 校验完整的成功或失败结果 |
| `invalidInputError` | 把输入校验问题映射为本领域安全错误，保留字段级错误 |
| `mapError` | 把业务异常映射为本领域安全错误 |
| `fallbackError` | 本领域固定的安全兜底错误 |
| `handler` | 接收解析后的输入和 Main 内部调用上下文，返回同步结果或 Promise |

来源不可信统一返回 `UNTRUSTED_SOURCE`。业务回调可以访问取消和请求归属所需的 sender 上下文，但不承担来源校验。注册器返回清理函数，封装 `removeHandler`；业务模块继续负责自己的活动请求与生命周期清理。

通过 schema 推导输入和返回值类型，约束错误映射与对应结果协议兼容；不得通过 `any`、`@ts-ignore` 或无约束类型断言绕过检查。

### 来源检查

集中保留现有检查语义：sender 未销毁、对应应用 BrowserWindow、senderFrame 存在且为 sender 的主 frame、frame URL 精确匹配 Main 配置的可信 Renderer URL。开发和打包环境均由现有启动逻辑提供 URL。

来源检查必须先于输入解析和服务调用。来源缺失、子 frame、非应用窗口、页面 URL 不匹配等情况均拒绝，不能因配置缺失而放行。此策略不替代业务权限或取消请求的所有权检查。

### 输入与异常处理

统一执行顺序：来源检查 → 输入 `safeParse` → 调用并等待 handler → 完整结果校验 → 返回解析后的结果。

- 输入失败不调用业务服务，通过 `invalidInputError` 生成安全错误。
- 保留 models 的 `INVALID_BASE_URL`、`INVALID_API_KEY` 等错误，以及 preferences 的语言校验错误；不强制把所有输入错误改为 `INVALID_INPUT`。
- 注册器同时捕获同步 throw 和 Promise rejection。conversation 的输入解析迁入注册器，消除该路径的原始 Zod 异常。
- `mapError` 仅返回协议允许的错误码和安全字段。不得把异常 message、cause、stack、SQL、数据库路径、密钥或原始校验对象发送给 Renderer。
- 错误映射函数自身抛错时，使用固定兜底错误，避免递归调用错误映射。
- 原始原因保留在 Main/Core 内部，不新增原始 payload 或密钥日志。

### 返回结果校验

每个 channel 必须配置完整的 `resultSchema`，成功结果、业务返回的失败结果和守卫生成的失败结果都经过校验；向 Renderer 返回 schema 解析后的对象，不返回未经处理的原对象。

结果不符合协议时返回固定的安全兜底错误，不把结果校验失败误映射为用户输入错误，不暴露原始结果或 Zod 详情。注册阶段校验 `UNTRUSTED_SOURCE` 结果和固定兜底结果；配置不合法则阻止注册，避免运行时兜底再次校验失败。运行时动态错误映射若不符合协议，直接使用已验证的兜底结果。

沿用 shared 中的结果 schema；审查返回对象是否仅包含允许公开的字段，避免透传内部结构。Preload 现有结果校验继续保留，Renderer 仍只使用 `window.api`。

## 验收标准

1. 全部现有请求 channel 均由公共注册器注册，新增直接使用原始 `ipcMain` 的生产代码会被静态检查拒绝。
2. 合法窗口正常调用；已销毁 sender、无窗口 sender、缺失 frame、子 frame 和错误 URL 均被拒绝，服务调用次数为零。
3. 非法输入返回既定安全错误，服务调用次数为零；无参数入口也有明确输入契约。
4. 同步异常、异步拒绝、错误映射自身抛错均得到可序列化的安全结果，不向 Renderer 传播原始异常。
5. 完整成功结果和失败结果均经过 schema；畸形返回值或错误映射返回值转为安全兜底，非法固定兜底配置无法注册。
6. 通过包含模拟密钥、SQL、路径和 stack 的测试异常与额外返回字段验证敏感信息不会跨边界传出。
7. conversation 的正常发送、重试、完成、失败、取消及 sender 销毁行为保持正确；models 的连接测试与取消、两个 practice 模块的既有交互回归通过。
8. Preload 保持窄业务接口，不暴露原始 IPC；新增错误文案覆盖所有受支持语言。

```bash

```

补充 Electron 开发与打包预览环境的调用冒烟验证，确认两种 Renderer URL 均能通过守卫；需要新增跨模块测试时放在 `tests/integration/`，端到端测试放在 `tests/e2e/`。

本计划只调整 IPC 边界和错误协议，不涉及数据库迁移或已有持久化数据变更。若实施中发现需要变更持久化数据，应遵循项目约定另行询问用户。
